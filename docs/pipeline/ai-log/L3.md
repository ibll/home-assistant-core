**What the AI did:**

- **Studied the real data first.** It read real run, job and artifact data
  from the GitHub API to learn the job naming (`Stage / step`). It found that
  the deploy job's created→started gap is the staging-approval wait, and that
  no `flaky*` artifacts exist yet.
- **Wrote the code.**
  - `.github/scripts/team_metrics.py`: pure calculation functions, kept
    separate from the `gh api` calls.
  - `.github/workflows/team-metrics.yml`: nightly plus manual runs,
    `actions: read`.
  - [metrics.md](../metrics.md)
- **Tested it.**
  - Ran the script on Python 3.14 against 60 days of real runs (54 runs).
  - Wrote offline checks, kept outside the repo, with made-up data whose
    answers are known: zero runs, success rate that leaves out manual runs,
    reruns, queue time, approval wait, change-failure rate, time to restore,
    lead time, both token formats, flaky counts and percentiles. All pass.
- **Linted it:** ruff 0.16.8 (the repo's pinned version and configuration),
  zizmor 1.30.1 `--pedantic`, yamllint and actionlint all pass.

**Problems the AI caught in its own first draft:**

- **Token totals that could mislead.** The first version summed tokens and
  reported 0 for D6's release-notes job. The real artifact showed
  `tokens: null`, because `actions/ai-inference` doesn't report usage, and
  `status: invalid`. Without a note, 0 tokens would read as "free and
  working". It added `runs_reporting_tokens` and a count of each output
  `status`.
- **Numbers that looked contradictory.** The stage table showed 11 deploy
  failures but a 0% change-failure rate. It broke the failures down (D1–D4
  branch test runs, `smoke` injections, two release-tag pushes) and wrote
  that down instead of leaving the numbers to look contradictory.
- **Ruff findings:** PERF401 (a comprehension instead of `append` in a loop),
  RUF002 (an en dash in a docstring), and INP001 (a "missing package"
  warning). INP001 is suppressed with a written reason: this is a standalone
  script, not a package.
